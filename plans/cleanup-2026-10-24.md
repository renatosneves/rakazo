## 3. How the fork works from now on

- `main` = upstream `main` plus one commit that removes upstream's workflows, so nothing runs or bills on the fork.
- `upstream-main` = upstream `main` exactly. `upstream-release` = the latest upstream release tag (now v0.3.3).
- `fold7-apk` = upstream `main` with every not-yet-merged feature merged in, plus the one build-only APK workflow. A push builds the APK and republishes https://github.com/renatosneves/rakazo/releases/tag/fold7-next
- New feature: branch `pr/<name>` from upstream `main`, one focused commit, tests run, then an upstream PR from that branch (Renato opens it through a prefilled link, because Claude cannot open PRs on elie222/rakazo). Pushes to the branch update the open PR. Merge it into `fold7-apk` for the test APK.
- After an upstream release or merge: move `main`, `upstream-main` and `upstream-release` forward, merge upstream `main` into each open PR branch (no history rewrites), rebuild `fold7-apk` on the new upstream `main` and drop features upstream now has.
- Not carried into the new APK yet: docked computer beside the chat and tabletop posture. Upstream's new fold-regions code replaced what they were built on, so they need rebuilding on top of it.
- Kept on the fork only: Android live working status on by default (`pr/live-status-default`). Upstream store builds can deliver pushes through Firebase, so turning it on for everyone is a product call for the maintainer.
